# 传感器读取原理

## 结论

MacBook 内置的环境光传感器在 macOS 上没有官方公开的框架可以读——和 iOS 情况一样（详见姊妹项目的 [doc/3-iOS光线传感器限制.md](../../light-for-better-sleep/doc/3-iOS光线传感器限制.md)）。这个项目最终用的是**完全公开、有文档的 IOKit registry 调用**读一个未文档化但公开可读的属性，全程没有用任何私有 API。

## 走过的弯路：私有 HID 事件接口

最初的计划是走苹果私有/未文档化的 `IOHIDEventSystemClient` HID 事件接口——和显示器亮度工具 [Lunar](https://github.com/alin23/Lunar) 用的是同一类技术。这条路先做了原型，能编译、能链接，但在这台机器（2022 款 MacBook Air, M2, Mac14,2）上，ALS 的 HID 服务始终没能通过这条路径返回事件——服务挂在一个厂商自定义的 usage page 下，不是标准的 HID "Ambient Light" usage，实测 `IOHIDServiceClientCopyEvent` 一直拿不到数据。

## 实际用的方式：公开的 IORegistry 属性

`Sources/FirstLight/AmbientLightSensor.swift` 直接读传感器 IOService 节点上一个实时的 `CurrentLux` 属性。这个节点的位置：

```sh
ioreg -p IOService -n als -l
```

能看到 `als`（`AppleSPUHIDInterface`）往下几层，有个 `AppleSPUVD6286` 节点（实际的传感器驱动类），带着一个 `CurrentLux` 属性。

验证过它是真·实时数据，不是开机快照：
- 数值在两次轮询间隔几分钟内变了（833 → 917）
- 旁边一个 `IOHIDEventServiceUserClient` 的 `EnqueueEventCount`（HID event type 12，即 `kIOHIDEventTypeAmbientLightSensor`）在持续递增，说明底层传感器一直在上报，这个属性是跟着一起变的

读取只使用**完全公开、有文档**的 IOKit registry 调用。程序先用
`IOServiceGetMatchingService` 查找实测机型上的 `AppleSPUVD6286`；如果找不到，
再用 `IORegistryCreateIterator` 遍历服务，自动发现带有数值型 `CurrentLux` 属性的节点；
最后通过 `IORegistryEntryCreateCFProperty` 读取数值。整个 App 没有使用任何私有 API。

## 刷新速率实测

用 2ms 间隔连续读了 45 秒，只记录数值真正变化的时刻：光照稳定时可能几十秒都不变一次（这是光照本身稳定，不是驱动慢），但只要光照真的在变，变化间隔最短能到 **0.2 秒**。据此把 App 的轮询间隔从最初的 2 秒调到了 0.25 秒——再快就是在重复读同一个缓存值，没有意义。

## 已知的脆弱点

`AppleSPUVD6286` 和 `CurrentLux` 是**这台 Mac 具体的驱动类名**和一个“能读但没文档”的属性 key——都不是苹果承诺稳定的契约。程序现在不会只依赖固定驱动类名：快速路径失败后会在 IORegistry 中自动寻找 `CurrentLux`。但如果未来系统连属性名也改掉，读取仍会失败。

如果 App 显示"传感器不可用"，按下面步骤重新诊断：

1. 右键菜单栏图标，打开“调试状态”，点击“复制兼容性诊断”，记录机型、系统版本、驱动类名和发现方式
2. 跑 `ioreg -p IOService -n als -l`，找找 `als` 这条链路下面哪个节点还在暴露一个数值看起来合理的实时属性
3. 确认它是实时的（两次间隔几分钟重新读一次，看数值有没有变；或者看旁边有没有 HID event count 在递增）
4. 如果属性名不再是 `CurrentLux`，需要为新机型补充新的候选属性和验证逻辑
